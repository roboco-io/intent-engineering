The Concept

Why Intent Engineering exists, how it relates to what came before, and what it changes about the way we build software.

The bottleneck has moved

For fifty years, software engineering optimized for a single constraint: code is expensive to write. We invented design patterns, code review, CI/CD, microservices, agile — all to manage the cost and risk of humans writing code.

Vibe coding dissolved that constraint overnight. AI agents can now generate, review, test, and deploy code faster than any human team. The staff SWE who ships 10,000 commits in six months is no longer science fiction — it's Tuesday.

But a new bottleneck emerged: intent. When code is free, the scarce resource is knowing what to build, why to build it, and what not to build. Without clear intent, AI produces mountains of technically correct but strategically useless output.

Intent Engineering is a paradigm that accepts this shift. It puts all human effort into precisely documenting intent, and delegates everything downstream — spec generation, implementation, verification, deployment — to AI.

What Intent Engineering is not

It is not prompt engineering. Prompt engineering optimizes how you talk to AI in a single session. Intent Engineering defines a persistent, evolving document that shapes all sessions.

It is not a design doc. Design docs prescribe how to build something: architecture, tech stack, timelines, milestones. Intent Documents explicitly exclude How. Implementation decisions are AI's domain.

It is not a PRD. Product requirement documents are comprehensive and static. Intent Documents are minimal and alive. They evolve through exploration, and they can be killed.

It is not a framework or tool. It's a markdown file and a discipline. You can adopt it today in any project with zero dependencies.

The three layers

An Intent Document has exactly three content layers. Anything beyond these is noise that confuses AI and wastes human attention.

Why — the reason this exists

The problem being solved, the goal if successful, and how to measure success. In exploration phase, the Why is a hypothesis — a bet that might be wrong. In clarified phase, the Why is conviction backed by evidence. If the Why changes fundamentally, that's a pivot, and it should be rare and deliberate.

What — the thing being built

Features, user flows, and edge cases. Written concretely enough that AI can derive tasks from it, but never prescriptive about implementation. "Users can export reports as PDF" is good. "Use puppeteer to generate PDFs via headless Chrome" is How, and it doesn't belong here.

Not — the boundaries that must not be crossed

This is the most underrated layer. Security constraints, scope limits, quality bars, forbidden patterns. Without Not, AI will make reasonable-looking decisions that violate your unstated assumptions. "Never store production keys locally." "No any types." "Mobile is out of scope." These lines save you from AI's optimistic helpfulness.

Learnings — the evolution engine

People rarely know what they want at the start. An idea begins as a seed — vague, uncertain, full of assumptions. The path to clarity runs through exploration: building prototypes, interviewing users, studying competitors, failing fast.

Learnings is a timestamped log of these explorations and their outcomes. Each entry records what was tried, what was discovered, and what changed as a result. This serves two purposes:

For the human: it creates an audit trail of decisions. When you look back at why the project pivoted, the answer is in the Learnings, not in someone's memory.

For the AI: it provides context that no amount of code can. An AI reading the Learnings section understands not just what the project is, but how it got there and what was already tried.

The lifecycle

Intent is not static. It moves through four states:

StateDescriptionWhat to do
seed Just an idea. Why is a guess, What/Not are empty or vague. Write a hypothesis. Start your first experiment.
exploring Actively testing the hypothesis through prototypes, research, interviews. Run experiments. Record learnings. Update Why/What/Not as you go.
clarified All three layers filled with conviction. No uncertainty markers. Hand off to AI. Build it.
killed Evidence shows this isn't worth building, or an existing solution covers it. Record why. Move on. This is a good outcome.

The most important transition is any state → killed. Knowing when to stop is harder than knowing when to start. A well-documented kill saves months of wasted effort and prevents the same dead-end from being explored again.

Relationship to existing concepts

ConceptScopeRelationship to Intent Engineering
Context Engineering Per-task, ephemeral The Intent Document becomes the top-level context that frames all tasks.
Harness Engineering Tool and environment setup The Not layer is the source of truth for harness rules (CLAUDE.md, linters, CI checks).
Spec-driven Development Feature specification Specs are auto-derived from the What layer. Humans stop writing them.
Vibe Coding Code generation Vibe coding is maximally effective when intent is clear. Intent Engineering provides that clarity.

The automation pipeline

When Intent Engineering is fully operational, humans touch only two points in the pipeline: the very top (writing intent) and the very bottom (evaluating outcomes and updating intent).

  [Intent Document]     ← Human writes and maintains
         ↓
  [Spec Generation]     ← AI derives task list from Why/What/Not
         ↓
  [Implementation]      ← AI agents write code in parallel
         ↓
  [Verification]        ← AI cross-reviews, tests, lints
         ↓
  [Deployment]          ← CI/CD automates release
         ↓
  [Feedback]            ← User data flows back
         ↓
  [Learn & Decide]      ← Human evaluates, updates intent or kills

Everything between intent and feedback is automatable today. Context engineering, harness engineering, spec writing — all of it can be derived from a well-written Intent Document. The human's irreducible job is deciding what matters and what we learned.

Why it works

Constraints breed creativity. By limiting the document to Why/What/Not, you force yourself to think about what actually matters. Every other format — PRDs, design docs, project plans — lets you hide behind detail. Intent Engineering leaves you nowhere to hide.

AI is better at How than you are. AI has read every architecture pattern, every framework doc, every Stack Overflow answer. Telling it how to implement something limits it to your knowledge. Telling it what to achieve unlocks its full capability.

Killing is productive. Most engineering cultures treat abandoned projects as failures. Intent Engineering treats a documented kill as a learning asset. The Learnings section of a killed project might be more valuable than the code of a shipped one.

Intent precision scales. One clear sentence in the Why section — "new users experience first value in 30 seconds" — propagates through every AI-generated task, every code review, every test. Vague intent produces vague code. Sharp intent produces sharp systems.

Getting started

Create a file called INTENT.md at the root of your project. Fill in Why. Be honest about What and Not — leave unknowns marked with (?). Start exploring. Record what you learn. Update or kill when evidence demands it.

That's Intent Engineering. No framework to install. No tools to configure. Just a discipline of knowing what you want and writing it down.
